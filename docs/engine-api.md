# Engine API contract

This is the contract between the React UI and the Rust engine, exposed through Tauri commands and events. Covers Epic 1, Stage 1a (`specs/01-foundation-specification.md`, FR-1.1–FR-1.40). Stage 1b added positional audio and the in-game overlay; Epic 2 (`specs/02-multi-server-themes-specification.md`) makes the API multi-server (see [Several servers](#several-servers)).

- **Source of truth:** Rust types and handlers in `src-tauri/src/commands/<area>.rs`, registered in `specta_builder()` in `src-tauri/src/lib.rs`.
- **Generated TypeScript:** `ui/src/bindings/commands.ts`. It is regenerated by debug runs and by `cargo test -p mumcord`. Never edit it by hand.
- **UI access:** always go through `getApi()` from `ui/src/api`, never the bindings directly. See [UI client and mock](#ui-client-and-mock).
- **Naming:** Rust `snake_case` commands become camelCase in TS (`identity_get` → `api.identityGet()`). Payload fields are camelCase. Simple enums are camelCase string literals; enums with data are tagged objects (`kind`, `state` or `status` field).
- **Numbers:** ids are `u32` (TS `number`) and times are RFC 3339 strings, because 64-bit integers are not exported to TS.
- **Optional values:** `Option<T>` is a required field of type `T | null`.

## Errors

Every command returns `Result<T, ApiError>`, with `ApiError = { code: ErrorCode, message: string }`. In the UI client a failure rejects with `EngineError` (`code`, `message`). `message` is technical detail or the server's denial text. The UI shows a plain-language text based on `code`. Messages never contain secrets.

| Code                       | Meaning / typical source                                                                                                                          |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| `notImplemented`           | Contract exists, engine part not built yet (all stubs today).                                                                                     |
| `notConnected`             | The command needs an active connection.                                                                                                           |
| `serverUnreachable`        | DNS failure, connection refused or timeout.                                                                                                       |
| `wrongPassword`            | Server password rejected.                                                                                                                         |
| `nameInUse`                | Username already in use or registered to someone else.                                                                                            |
| `certificateRejected`      | Server rejected the client certificate, or the user declined to trust the server certificate.                                                     |
| `certificateChanged`       | A trusted server presented a different certificate (FR-1.10).                                                                                     |
| `serverTooOld`             | Feature needs a newer server, e.g. following needs ≥ 1.4 (FR-1.12).                                                                               |
| `permissionDenied`         | The server's ACL denied the action; `message` has the server's reason.                                                                            |
| `listenerLimitReached`     | The server's channel-listener limit is reached (FR-1.31).                                                                                         |
| `messageTooLarge`          | Message, image or avatar exceeds the server limit (FR-1.30).                                                                                      |
| `invalidInput`             | Bad argument: empty name, bad address, malformed link, out-of-range volume.                                                                       |
| `notFound`                 | Unknown server, channel, person or file; also "no identity yet".                                                                                  |
| `secureStorageUnavailable` | OS secure storage unavailable or access refused (FR-1.3, FR-1.8).                                                                                 |
| `io`                       | Reading or writing a local file failed.                                                                                                           |
| `shareFull`                | The screen share already has 8 viewers (FR-2.43).                                                                                                 |
| `directUnavailable`        | Watching a screen share needs a direct connection and none can be made (FR-2.46); `message` is `consentOff`, `peerUnsupported` or `noDirectPath`. |
| `serverLimitReached`       | The "connected servers" limit would be exceeded (FR-2.1); `message` names it.                                                                     |
| `shortcutNotConfirmed`     | Wayland: the desktop did not confirm the PTT shortcut (dismissed, no key, portal error).                                                          |
| `internal`                 | Unexpected failure. In the UI also used for framework-level IPC errors.                                                                           |

Some server denials arrive later, not as a reply to a command. Those come as the `serverDenied` event.

## Several servers

Epic 2 lets Mumcord be connected to several servers at once (FR-2.1). The API carries the server everywhere:

- **Commands** that act on a connection take `serverId` (the saved server's id) as their first argument: `disconnect`, `reconnect_cancel`, `session_snapshot`, `connection_stats`, the channel, people, chat, follow, history-load/sync and own-profile commands, `full_image_fetch`/`full_image_cancel`, watch party and screen share. A `serverId` that is not connected fails with `notConnected` (or returns `null` / does nothing where noted).
- **Global commands** stay without it: identity, saved servers, settings, audio, push-to-talk, positional audio and the in-game overlay (both always follow the voice server), self mute/deafen (voice server), link previews and GIFs, friends, app and notifications.
- **Events** about one server carry a top-level `serverId`: `connectionStateChanged`, `transportChanged`, `serverDenied`, channel, people, talk, follow, unread, chat, history sync, `fullImageProgress`, `nowPlayingChanged`, `nowGamingChanged`, `positionalSendingChanged`, `userStatsChanged`, `watchPartyChanged`, `screenSharesChanged`, `directConsentRequired`. `certTrustRequired`, `serverSynced` (in the snapshot) and `defaultAvatarSkipped` already had it.
- **Several sessions** (B4a): the engine holds one session per connected server, up to `maxConnectedServers`; every event carries the id of the server it belongs to (also its final `disconnected`). Session, channel and people commands act on the given server. Chat, follow, history and history sync, own-profile, full-image, Mumcord peers, now playing/gaming and friends work per server too (B4b): their commands act on the given server (`friendAdd`, `nowPlayingCover`, `nowGamingIcon` and `nowGamingJoin` take a `serverId`), now playing/gaming is shared on every connected server, and a friend's `online.serverId` names the server they are on (they can be online on several; the lowest server id is shown).
- **Stubs:** commands marked **Stub.** below are typed and registered but answer `notImplemented` until their task builds them.

## Shared types

- `ServerId`, `ChannelId`, `SessionId` are `number`. Channel and session ids are only valid for the current connection.
- `Conversation`:
  - `{ kind: "channel", channelId }`
  - `{ kind: "private", certHash }`: private chat with a person, kept across sessions.
  - `{ kind: "privateSession", session }`: private chat with a person who has no certificate; lasts only for the session.

`Settings` fields:

- `wizardCompleted`: boolean.
- `theme`: `system` / `dark` / `light`.
- `language`: `en` / `es` / `de`, or `null` to follow the OS.
- `talkMode`: `voiceActivation` / `pushToTalk`.
- `voiceActivation`: `automatic` (default, speech detection) / `manual` (FR-1.57). Only matters in `voiceActivation` talk mode. In `manual` the mic opens when the processed input level (after echo cancellation, noise suppression and automatic volume, the same value the `micLevel` meter shows) reaches `voiceThresholdDbfs`; the gate opens on the first 10 ms frame, stays open 300 ms after the level drops and uses 3 dB of hysteresis.
- `voiceThresholdDbfs`: integer, -60 to 0, default -40; clamped on save. Map to the 0–1 `micLevel` scale with `(dbfs + 60) / 60`.
- `pttKey`: string or `null`; a keyboard shortcut (`"Ctrl+A"`) or a mouse button (`"MouseMiddle"`, `"Mouse4"` = back, `"Mouse5"` = forward).
- `allowMouseButtons`: boolean, default `false`. Linux Wayland only: "Allow mouse buttons (requires input group)".
- `pttCompatibilityMode`: boolean, default `false`. Linux Wayland only: "Compatibility mode (X11)". Read before GTK starts: when on, Mumcord sets `GDK_BACKEND=x11` (unless the user set it), runs through XWayland and uses the X11 push-to-talk path for keys and mouse buttons (no portal, no evdev). Takes effect after `app_restart` (FR-1.48).
- `inputDevice`, `outputDevice`: device id, or `null` for the OS default.
- `noiseSuppression`, `echoCancellation`, `autoGain`: boolean.
- `musicQuality`: boolean, default `false` (FR-1.24, QA.37). Off: the automatic send bitrate is capped at 96 kbit/s (speech). On: the cap is the server limit minus 10 % headroom and packet overhead, at most 510 kbit/s; the Opus encoder switches to the audio application with the music signal type; noise suppression and automatic volume are bypassed (they damage music). The bitrate still drops on packet loss and recovers afterwards; `sendBitrateKbps` in `connection_stats` shows the current value. Applies immediately, also while connected. Voice activation may not open for music, so push-to-talk is advised.
- `sounds`: `{ joinLeave, selfMute, selfDeaf, messages, voiceJoin, hangUp }`. `voiceJoin` plays when the user joins a channel for voice themselves (join command or a link with a channel; not the read-only landing or a reconnect). `hangUp` plays on `disconnect` and when `connect` replaces a connection with voice on, not on quit or connection loss.
- `notifications`: `"inApp" | "desktop" | "both" | "off"` (default `"both"`, FR-1.48c). In-app: toasts while the window has focus, nothing otherwise. Desktop: system notifications, also while focused. Both: toasts while focused, system notifications otherwise. Never for the chat on screen while focused.
- `closeBehaviour`: `ask` / `minimizeToTray` / `quit`.
- `chatDisplay`: `"cozy" | "compact"` (default `"cozy"`, FR-1.48a, QA.25). Cozy: avatar per message group, name and time above the indented text. Compact: no avatars, time, name and text on one line.
- `logLevel`: `error` / `warn` / `info` / `debug`.
- `sendDefaultAvatar`: boolean, default `true`. On the first connect to a saved server, the default avatar is sent if one is set and the user has no avatar there yet, scaled to the server limit. Each saved server is handled only once, whatever the outcome (setting off, no default avatar, already an avatar there, sent, or too large): it is never sent there again, even after the user removes or replaces the avatar manually. Only failures such as a lost connection or a denial leave the server unhandled for the next connect (FR-1.47). A sent default avatar becomes the avatar remembered for that server (see `set_own_avatar`), so it is sent again whenever the server has forgotten it (QA.10).
- `autostart`: boolean, default `false` (FR-1.48d). Changing it adds or removes the OS login entry (Linux `$XDG_CONFIG_HOME/autostart/app.mumcord.client.desktop`, macOS `~/Library/LaunchAgents/app.mumcord.client.plist`, Windows `HKCU\…\Run\Mumcord`) before saving; if that fails, `settings_update` fails with `internal` and nothing is saved. Every start rewrites the entry for the current program path (e.g. a moved AppImage) or removes a leftover one. The entry starts Mumcord with `--autostart`.
- `startMinimized`: boolean, default `true`. A start through the login entry keeps the window hidden in the tray (minimized to the taskbar if no tray is available); a manual start always shows the window.
- `connectMuted`: boolean, default `true` (FR-1.14, QA.22). On: a fresh connect without a link lands read-only (self-muted and deafened) until the user joins a channel. Off: it lands in the default channel with the user's last own mute/deafen choice applied right away, without the read-only hint and without the join sound; the rejoin prompt (QA.9) is still offered. A link with a channel path and an automatic reconnect behave as before. Read at each connect, no restart needed.
- `linkPreviews`: boolean, default `true` (FR-1.49, QA.34). "Show link previews and embeds", offered in the first-start wizard (step 3) and under Settings → Chat & history. Off: messages show plain links and `link_preview` makes no request.
- `offerFullImages` / `loadFullImages`: booleans, default `true` (FR-1.74, QA.72). "Offer my full-size images" and "Load full-size images from others" under Settings → Chat & history; see "Full-size images".
- `previewCacheDays`: number or `null`, default `7` (QA.42). "Delete cached previews after X days" under Settings → Chat & history (1 / 7 / 30 / never). Values below 1 are stored as 1. Applied at start, hourly and right after a change.
- `historyMaxAgeDays`: number or `null`, default `null` (keep everything; QA.42). "Delete chat history older than X days" under Settings → Chat & history (7 / 30 / 90 / 365). Deletes messages sent before now minus X days on every server, without confirmation, at start, daily and right after a change; local history only.
- `nowPlaying`: boolean, default `false` (FR-1.58, QA.40). "Share what I'm listening to" under Settings → Profile. Off: the media player is not read, nothing is shared and the comment line is removed.
- `nowGaming`: boolean, default `false` (FR-1.59, QA.44). "Share the game I'm playing" under Settings → Profile and in the quick settings. Off: no programs or Steam files are read, nothing is shared and the comment line is removed.
- `historySharing`: boolean, default `true` (FR-1.60). "Share my channel history" under Settings → Chat & history and in the first-start wizard. On: other Mumcord users who may read a channel can fetch its stored messages from before they joined it (never private chats). Off: history sync requests are not answered.
- `maxConnectedServers`: 1–15, default 5, clamped on save (FR-2.1).
- `appThemeId`: id of a built-in preset or a `customThemes` entry, default `"mumcord-dark"`; empty falls back to it (FR-2.14).
- `customThemes`: `ThemeRecord[]`, `{ id, name, colors }` with `colors` mapping the key colours (`background`, `surface`, `text`, `accent`, `talking`, `warning`, `error`) to `#rrggbb`. Values that are not such a colour are dropped on save, since themes also come from chat messages (FR-2.16).
- `visualEffects`: boolean, default `true` (FR-2.19). `hideEmptyChannels`, `talkingFirst`: booleans, default `false` (FR-2.23). `showWeakConnectionIcon`: boolean, default `true` (FR-2.26).
- `allowDirectConnections`, `updateCheck`, `appimageMenuEntry`: `"unset" | "yes" | "no"`, default `"unset"` = not asked yet (FR-2.36, FR-2.56, FR-2.55).
- `windowOverlayNoticeShown`: boolean; the one-time "window overlay removed" notice was shown (FR-2.33).
- `whatsNewAuto`: boolean, default `true`; open "What's new" once after an update (issue #145). `whatsNewSeen`: the display version whose "What's new" was shown or skipped, `null` before the first start that knew about it.
- `positional`: `{ enabled, minDistance, maxDistance }`, default `{ false, 1, 15 }` (FR-1.41). Distances in metres: full volume up to `minDistance`, silent beyond `maxDistance`; saved as `0 ≤ min < max ≤ 1000` with `max ≥ min + 1`. Off: no game positions are read, nothing is sent and voices play unplaced.

Mouse push-to-talk (FR-1.21, QA.4): `native` support means a Windows low-level mouse hook, a macOS listen-only event tap (`accessibilityMissing` if the system refuses it; the system prompt is shown) or X11 XInput2 raw button events. `evdev` (Linux Wayland) reads input devices directly and only while `allowMouseButtons` is on: it opens only mice (`BTN_LEFT` and relative motion, no letter or digit keys), never grabs them, evaluates only the configured button and logs no input; mice plugged in later are picked up. Its `state` is the device permission, checked without opening a device, also while the setting is off. `inputGroupMissing`: the UI shows `sudo usermod -aG input $USER`, then log out and in. `mouseDisabled`: a mouse key is stored but `allowMouseButtons` is off.

## Link previews and player cards

`mumble_link_stats` (issue #175) answers the public query for one `mumble://` link: `MumbleLinkStats` is `privacyOff` while the `linkPreviews` setting is off, `unreachable` when the server does not answer the query in three seconds, and `answered { pingMs, users, maxUsers, version }` otherwise. Only the engine contacts the network, and the query never connects: it is the "extended information" UDP ping, sent in the protobuf form for servers from 1.5 and in the legacy form for older servers, and the value the query carried must come back unchanged before the answer is taken. Answers are kept for the run (at most 200 servers, 60 seconds for a good answer, 10 minutes for a missing one); `refresh` asks again, which is what the card's Retry button does. The reply is untrusted input: fixed layout, length-checked, and the UI renders every field as plain text.

`mumble_link_join` (issue #175) handles the click on a card's Join with the same rules as a link from outside (FR-2.13): the server is brought into view, a running connection joins the channel of the link, and an unknown server is offered for saving. Nothing here happens without a click. The card is shown even with link previews off, but no query is sent then: it says that the setting is off instead of showing figures.

`link_preview` (FR-1.49, FR-1.50) returns `LinkPreview { url, siteName, title, description, image, video, isImage }`. All text is plain text (whitespace collapsed, control and bidi characters removed, length-limited); the UI renders it as text, never as HTML. `image` is a `data:image/jpeg|png` URL: the engine fetches the preview image itself, decodes it with size limits, scales it to at most 480 px and re-encodes it, so the webview never loads anything from the linked site. `video` is set for YouTube (`youtube.com/watch`, `youtu.be`, `/shorts`, `/live`) Twitch (channel, `/videos/<id>`, clips) and Spotify (`open.spotify.com/{track,album,playlist,artist,episode,show}/<id>`, optional `intl-xx/` prefix, query like `?si=` ignored) links: `VideoEmbed { site: "youtube" | "twitch" | "spotify", playerUrl, channel }`. For Spotify `channel` is the kind of item (`track`, `album`, …) and `description` is the artist/owner line from the page's OpenGraph tags.

- **Fetching** (`crates/engine/src/web/`): GET with a neutral User-Agent, no cookies, no referrer, no proxy, 4 s connect / 8 s total timeout, at most 3 redirects, HTML read up to 512 KB (only `<head>` metadata is used: OpenGraph, Twitter cards, `<title>`, `<meta name="description">`), images up to 2 MB (PNG, JPEG, GIF, WebP, detected from the bytes). YouTube titles, uploader and thumbnail come from YouTube's public oEmbed endpoint; Twitch from the page's OpenGraph tags; Spotify title and cover from Spotify's public oEmbed endpoint (`open.spotify.com/oembed`, no key), falling back to the page's OpenGraph tags.
- **SSRF guard:** private, loopback, link-local, carrier-grade NAT, multicast, documentation and other non-public addresses (IPv4 and IPv6, including IPv4-mapped and 6to4) are never contacted. Host names are resolved by a resolver that drops such addresses at connect time, so DNS rebinding and every redirect hop are covered; IP literals are checked before the request and on each redirect. E2E builds (`test-backend`) can restrict fetching to given addresses with `MUMCORD_TEST_PREVIEW_ADDRESSES`.
- **Cache:** every result (also "no preview") in memory, successful previews also on disk in `<data dir>/link-previews/` (one JSON file per URL hash, at most 300 files) for `previewCacheDays` days (default 7, QA.42). Thumbnails and preview images are part of the cached preview, so one clean-up covers all of them. Expired files are deleted at start, hourly and after the setting changes, off the UI thread; `preview_cache_clear` deletes everything. Failures are retried after 10 minutes (memory only).
- **Player:** the UI loads the player only after the user clicks play (`sandbox="allow-scripts allow-same-origin allow-presentation"`). Spotify's `playerUrl` is framed directly; YouTube and Twitch run inside the loopback page `embed.html` (FR-2.41a, see Watch party), which frames `playerUrl` and appends Twitch's `parent`. The CSP in `src-tauri/tauri.conf.json` allows `frame-src` for exactly `http://localhost:*` (the loopback page, which itself may only frame `https://www.youtube-nocookie.com`, `https://player.twitch.tv` and `https://clips.twitch.tv`) and `https://open.spotify.com/embed/` (Spotify only on the embed path); images stay limited to `'self' data: blob:`.
- **Platform limits:** YouTube refuses to play without an http(s) referrer, which pages served from Tauri's `tauri://` scheme (Linux with WebKitGTK, macOS) cannot send; Twitch only accepts an HTTPS or `localhost` parent. Both therefore play through the loopback page on every platform. Spotify's embed needs neither, so its player is loaded directly; this could not be checked on WebKitGTK, WebView2 and WKWebView without internet access in the build environment, so verify it on a real Spotify link. When the loopback page cannot be opened, the play button opens the link in the system browser instead.
- **Image links:** a link whose response has an `image/*` content type yields `LinkPreview { isImage: true }` (no card); the UI shows it with `inline_image` instead.

## Inline images

`inline_image` (FR-1.55, QA.35) returns `InlineImage { url, src, width, height, animated }` for external images in messages and direct image links. Chat messages keep absolute http(s) `<img src>` URLs through the engine sanitizer (`sanitize_message_html`; comments and welcome texts never do); the UI sanitizer still removes these images from the message text and shows them under it instead. The UI treats links whose path ends in `.png`, `.jpg`, `.jpeg`, `.gif` or `.webp` as images directly, and other links as images when `link_preview` reports `isImage`.

- **Fetching:** the same guarded fetcher as link previews (SSRF guard incl. redirects, timeouts), up to 16 MB. Known GIF hosts first try smaller renditions (Giphy: `giphy-downsized-large.gif`, then `giphy-downsized-medium.gif` in place of an original `giphy.gif` or `giphy.webp` on `media*.giphy.com`, so the chat animates a box-sized GIF instead of the full-size file; page links `giphy.com/gifs/<slug>-<id>` resolve by id, `tenor.com/view/<slug>-<id>` by the page's `og:image`); `link_preview` reports `isImage` for these page links. The result keeps the link as posted. The format is sniffed from the bytes (PNG, JPEG, GIF, WebP); the server's content type is ignored. Images larger than 8192 px per side are refused.
- **Delivery:** `src` is always a `data:` URL, so the CSP stays unchanged. Still images are decoded with limits, scaled to at most 800 px per side (twice the 400×300 chat box) and re-encoded as JPEG or PNG. Animated GIF and WebP pass through unchanged so they keep moving, if no side exceeds 2048 px. `width`/`height` describe `src`, so the UI reserves the right box (a fixed 400×300 placeholder while loading).
- **Cache and privacy:** cached like previews in `<data dir>/link-previews/images/` (at most 150 files) and removed by the same `previewCacheDays` clean-up and "Clear now". Dismissing uses `preview_dismiss` with the image URL. Off switch (`linkPreviews`): nothing is fetched, the images are not shown (AC-1.13 behaviour).
- **Click:** the UI's `onImageClick` hook (image viewer, B42); until then a click opens the image in the browser.

## Full-size images

Full-size chat images (FR-1.60c, QA.57) between Mumcord clients (`crates/engine/src/full_image/`).

- **Sending:** the UI fits a thumbnail into the server's image limit as before and, when it had to shrink or recompress the picture, calls `full_image_keep` with the original. The engine keeps the original if it is a valid PNG/JPEG/GIF/WebP of at most 512 KiB and 3840 px per side, else a re-encoding (JPEG, or PNG with transparency) that fits. The thumbnail's `<img>` gets `data-mumcord-full="<sha256 hex>:<bytes>"`; official clients ignore the attribute and show the thumbnail. The engine and UI sanitizers keep the attribute only on message images and only in exactly this format.
- **Transfer:** plugin data with data id `mumcord.image`, binary messages `Get` (hash), `Queued`, `Start` (size), `Chunk` (index + up to 960 bytes) and `Unavailable`, each tagged with the requester's transfer id. The sender serves only images it sent itself, one transfer at a time (up to 4 waiting, 6 requests per person and minute), paced at about 2.9 messages per second to stay under the server's plugin message limit; that is about 2.7 KB/s, so a 512 KiB image takes about three minutes. The requester gives up after 10 s without an answer, 6 min in the queue or 15 s without a chunk.
- **Receiving:** only from the message's sender (found by certificate hash, else session) while online and only when that client announced the `full-image` feature in its Mumcord hello (FR-1.61). Chunks must arrive in order; the result must match the announced size and SHA-256 and decode completely within the limits above before it is shown.
- **Cache:** sent and received full images are cached in `<data dir>/link-previews/full-images/` (at most 100 files) and removed by the same `previewCacheDays` clean-up and "Clear now". After that, others get the thumbnail only.
- **Switches (FR-1.74, QA.72):** `offerFullImages` (default on): off makes `full_image_keep` fail with `invalidInput` (the UI then sends the thumbnail without reference) and every request from others is declined as unavailable. `loadFullImages` (default on): off makes `full_image_fetch` return `null` at once, without cache lookup or request; the viewer keeps the thumbnail without a hint. The `full-image` feature stays in the Mumcord hello in both cases: it is only sent at connect, so a later switch change could not be reflected, and a declined request is cheap.

### Watch party (FR-2.39 – FR-2.41, Beta)

- **Transport:** plugin data id `mumcord.watch`, JSON `{"v":1,"t":…}` of at most 1000 bytes, sent only to people in the user's channel whose Mumcord hello announced `watch-party`. Official clients never get it. Messages: `start {video}`, `join`, `leave`, `cmd {cmd: WatchCommand}` and `state {video, playing, pos, starter, members, last}`. Higher versions are read; unknown types, foreign video ids and senders outside the channel are ignored. The sender of a command is the session the server stamped, never a payload field; member lists are capped at 32 and checked against the channel.
- **Joining:** starting invites everyone; nothing plays until the user clicks "Join". Someone entering the channel later gets a `state` from the participant with the lowest session and starts at the current position (extrapolated while playing). The same `state` is sent once more about 3 s later, in case the server dropped the first (plugin data over its rate limit is lost silently); the newcomer keeps the first one it gets.
- **Leaving:** "Leave party", changing channel, leaving the server or disconnecting. Two parties started at the same moment resolve to the one of the lower starter session; the party ends when its last participant leaves.
- **Player (UI, FR-2.41a):** YouTube refuses to play inside the app origin of Linux and macOS release builds (`tauri://localhost`, error 153), so on every platform the UI frames a loopback page (`watch_party_player_url`, `player.html`) that frames the `youtube-nocookie.com` embed and drives it through YouTube's postMessage control protocol; no YouTube script runs in the app page. The app and the page exchange only typed messages (app → page `load {videoId}`, `play`, `pause`, `seek {seconds}`; page → app `ready`, `state {state}`, `time {seconds}`, `ended`, `error {code}`), each side checking the other's origin and frame. YouTube and Twitch cards in the chat play through the second page of the same server (`embed_player_open`, `embed.html`, one typed `embed {url}` message; the page checks the player URL again and sets Twitch's `parent` to `localhost` and the app's host). The server (`src-tauri/src/watch_player/`) binds 127.0.0.1 on a random port and is addressed as `http://localhost:<port>` (the name Twitch accepts without https); it answers only `GET /<128-bit token>/player.html` or `/embed.html` with `Host: localhost:<port>` or `127.0.0.1:<port>` (everything else 404), lets only the app origins frame the pages (`frame-ancestors`), logs no requests, starts on first use and closes its port once the user is in no party and no chat embed plays. If the player does not answer within 8 s, "Open in browser" is offered instead.

## Now playing

"Now playing" (FR-1.58) shares the track playing in the system's media player with others on the server; it is opt-in (`nowPlaying` setting).

- **Source** (`src-tauri/src/now_playing/`): read every 2 s off the UI thread, only while the setting is on. Linux: MPRIS over the session D-Bus (`org.mpris.MediaPlayer2.*`; a playing player wins over a paused one, Spotify over others; title, artists, album, `mpris:artUrl`, length, position). Windows: the system media session (`GlobalSystemMediaTransportControlsSessionManager`; no cover, Windows exposes it only as an image stream). macOS: not supported (no public API); `now_playing_status` reports `supported: false`.
- **Sharing** (`crates/engine/src/now_playing/`): plugin data (`PluginDataTransmission`, servers ≥ 1.4) with data id `mumcord.nowplaying` and the JSON payload `{"v":1,"title","artist","album","art","pos_ms","dur_ms","playing","ts"}` (`{"v":1}` = stopped), at most 1000 bytes (the server limit; the cover link goes first, then the album, then title and artist are shortened). Sent to everyone on the server on every change (track, play/pause, a seek of more than 3 s) and every 30 s, and to people who join. Received payloads are capped and sanitized; only http(s) cover links are kept.
- **Comment line:** official clients see `🎵 Artist – Title` at the end of the own comment while a track plays. It changes only after a change has lasted 5 s (no update per skipped track), is removed when playback pauses or stops, the setting is turned off or the user disconnects (best effort; a leftover line is removed on the next connect), and is left out if the comment would exceed the server's text limit. `set_own_comment` keeps the line; `person_profile` of the own session returns the comment without it.
- **Display:** `nowPlayingChanged` events; the UI anchors `positionMs` to the arrival time and advances it locally while playing. Music icon with tooltip next to the person while playing; cover, title, artist and progress bar in the profile card and preview.

## Now gaming

"Now gaming" (FR-1.59) shares the game being played with others on the server; it is opt-in (`nowGaming` setting). It mirrors [Now playing](#now-playing).

- **Sources** (`src-tauri/src/now_gaming/`, parsing in `crates/engine/src/now_gaming/detect.rs`): asked every 5 s off the UI thread, only while the setting is on, best first through the engine's `GameSource` trait (the Mumble Link source with game name and context arrives with positional audio, B30, in front of the others).
  1. The running Steam game. Linux: the app id of Steam's `reaper SteamLaunch AppId=<id> -- …` wrapper, which Steam starts every game under (its command line is world-readable, unlike the `SteamAppId` environment variable, and current Steam clients no longer write `RunningAppID` to `~/.steam/registry.vdf` – that file is only a fallback). Windows: `HKCU\Software\Valve\Steam\RunningAppID` (via `reg query`). macOS (best effort): `RunningAppID` in `~/Library/Application Support/Steam/registry.vdf`. The name comes from the bundled list, else from the game's `appmanifest_<id>.acf` in Steam's libraries (Linux/macOS; native, Flatpak and `~/.steam` installs) or `HKCU\Software\Valve\Steam\Apps\<id>\Name` (Windows).
  2. Running programs (Linux `/proc`, Windows `tasklist`, macOS `ps`) matched by executable name against the bundled list `crates/engine/src/now_gaming/games.json` (about 75 well-known games: name, optional Steam app id, executable names per OS; on Linux the Windows names count too, for Proton).
     Support: Linux and Windows full; macOS best effort (few macOS entries, Steam rarely records the running game there); other systems report `supported: false`.
- **Sharing** (`crates/engine/src/now_gaming/`): plugin data id `mumcord.nowgaming`, JSON `{"v":1,"game","steam_app_id","started_at","join"}` (`{"v":1}` = stopped; `started_at` in Unix ms of the sender; `steam_app_id` and `join` optional). Sent on every change and every 60 s, and to people who join. Received payloads are capped and sanitized; a start time in the future counts as now, and `join` is kept only when it is exactly `steam://connect/<host>:<port>` (plain host name or IPv4, port 1–65535).
- **Join target:** offered only when the own game was started with `+connect <host[:port]>` (Source engine games joined from a server browser; port 27015 when none is given). Lobby links and the Mumble Link context come later (B30). "Join game" asks for confirmation and then opens the link through the OS; other targets never get a button.
- **Comment line:** official clients see `🎮 Game` at the end of the own comment while a game runs; same rules as the now-playing line (5 s settle, removed when the game ends, the setting is turned off or the user disconnects). Both status lines can be present (music first); each feature only replaces its own.
- **Display:** `nowGamingChanged` events; the UI anchors `playedMs` to the arrival time. Controller icon with tooltip "Playing <game>" next to the person; game picture (or a generic controller), name and play time ("for 1 h 20 min") in the profile card and preview; "Join game" only in the profile card of another person. The own user panel status line shows the game in front of a playing track (one short line); its tooltip names both.

## Positional audio

Positional audio (FR-1.41–1.43, FR-1.72) places the voices of people in the same game around the listener. Engine: `crates/engine/src/positional.rs`; sources: `crates/positional`; rendering: `crates/audio/src/spatial.rs`.

- **Sources:** while `positional.enabled` is on, the engine asks its position sources every 20 ms (nothing is read while off). Today: the Mumble Link shared memory (`/MumbleLink.<uid>` on Linux/macOS, `MumbleLink` file mapping on Windows, official `LinkedMem` layout); a game counts as active while its `uiTick` changes and as gone 5 s after it stops. Then the enabled official Mumble game plugins in their stored order (`crates/positional/src/plugins/`): Mumble 1.4+ plugin libraries (C plugin interface, API 1.x), loaded only once the list is asked for or a plugin is enabled and called only on a dedicated `mumcord-plugins` thread. An enabled plugin gets the running programs every 2 s until it finds its game, then is asked for positions every 20 ms; it stops reading the game within 1 s once the engine stops asking (positional audio off). The context is sent as `<plugin name>\0<context>` like the official client does. A failing plugin is marked and left alone; the Mumble API handed to plugins answers every call with an error (logging is a no-op).
- **Sending:** the game context and identity go to the server as `UserState.plugin_context` (`"Link\0" + context`, like the official client) and `plugin_identity`; empty when no game runs. Once the server has the context, every outgoing voice packet carries the avatar position (legacy and protobuf voice format). The server forwards positions only between users with the same context.
- **Listening:** the game's camera pose is the listener; voices with a position are panned (equal power, narrowed for headphones), get an interaural delay and a far-ear low-pass, and are attenuated with distance. Without a game, or with the setting off, voices play unplaced.
- **"3D" icon:** a person whose voice packets carry a position is reported as sending (`positionalSendingChanged`) until 3 s pass without such a packet, independent of the own setting; the own session while Mumcord sends positions.

## Overlay

The floating overlay window of Epic 1 (FR-1.44–FR-1.46), its KDE window-rule helper, settings and tray item are removed (FR-2.33, QA.91); the in-game overlay below replaces it. `windowOverlayNoticeShown` remembers the one-time notice for users who had it on.

## In-game overlay

The in-game overlay (FR-1.46b, AC-1.34b, QA.54–QA.56) is drawn **inside the game's own frames** (not a window), so it shows in exclusive fullscreen too. It is a separate pipeline from the window overlay above, which stays the fallback where this is off or unsupported.

- **Platforms.** Linux: a Vulkan layer (`VK_LAYER_MUMCORD_overlay`, crate `mumcord-overlay-layer`, built as `libmumcord_overlay_layer.so`) that hooks `vkQueuePresentKHR`, plus an OpenGL fallback in the same library loaded with `LD_PRELOAD` (`glXSwapBuffers`/`eglSwapBuffers`). Windows (FR-2.28): no hook and no DLL; a separate transparent, click-through, always-on-top layered window (`windows_window.rs`) that never activates and is absent from the taskbar and alt-tab. Out-of-context WinEvent hooks (foreground, minimize, the game process's move/resize) tell Mumcord which window is in front. Its executable path is read with a `PROCESS_QUERY_LIMITED_INFORMATION` handle, and it counts as a game when the user configured it, it is on the bundled game list, or it runs from a Steam library (`steamapps\common`, keyed by Steam's `RunningAppID`). The window draws the same panel as the Linux layer (`mumcord_overlay_ipc::render`) in the configured corner of the game's client area. It is shown only while that game is in the foreground and hidden in exclusive fullscreen; `explanationKey` `overlay.inGame.limits.windowsFullscreen` is shown as a hint. Nothing touches the game, so the anti-cheat blocklist does not apply there (`BLOCKLIST_APPLIES`, `ingame_overlay::decide`); global and per-game on/off still do. macOS: none at all (QA.58; `SUPPORTED` is `false`, no window overlay either). `support()` in `src-tauri/src/ingame_overlay` returns `{ supported, explanationKey }`; on Linux it is supported only when the library is found (`MUMCORD_OVERLAY_LAYER`, else next to the executable, else `../lib/mumcord/`), otherwise `explanationKey` is `overlay.inGame.limits.libraryMissing`. `npm run build:overlay-layer` (run by `src-tauri/tauri.linux.conf.json` before `tauri dev`/`tauri build`) builds the library next to the app executable and stages it for the AppImage/deb/rpm, which install it as `/usr/lib/mumcord/libmumcord_overlay_layer.so`.
- **IPC.** Crate `mumcord-overlay-ipc` holds the protocol. Mumcord listens on a per-user abstract Unix socket `@mumcord-overlay-<uid>` (Linux; `MUMCORD_OVERLAY_SOCKET` overrides the name for isolated tests). It is abstract rather than a file in `$XDG_RUNTIME_DIR` because games in the Steam Linux Runtime (pressure-vessel, used by Proton) and Flatpak get a private runtime directory but share the host network namespace, where abstract sockets live. Abstract sockets have no file permissions, so both sides check the peer with `SO_PEERCRED`: Mumcord drops connections from other users, and the game refuses a listener owned by another user. A tiny versioned binary protocol (`wire.rs`, `VERSION`): the game sends `Hello { version, api, pid, steamAppId?, exe }`, Mumcord replies with `Config` (the per-game decision and look) and streams `Scene` (who is talking: names + talking/muted/deafened flags, the channel name) plus a `Heartbeat` every second. The game side reads non-blocking off the render thread and drops stale data (no heartbeat for 3 s → draw nothing); Mumcord never blocks on a stuck game (short write timeout, one thread per game).
- **Rendering.** The overlay is rasterized on the CPU into a premultiplied-RGBA panel (`render.rs`, bundled subset of Noto Sans Medium under SIL OFL 1.1, `crates/overlay-ipc/assets/`), then uploaded once per change and blended over the swapchain image (ONE / ONE_MINUS_SRC_ALPHA). Fail-open: any error, missing font or allocation failure draws nothing and never panics across FFI.
- **Install / uninstall.** Turning the global overlay **On** installs the Vulkan layer manifest into `"$XDG_DATA_HOME"/vulkan/implicit_layer.d/mumcord_overlay.json` (points at the `.so`, `disable_environment: MUMCORD_OVERLAY_DISABLE=1`); **Off** removes it, so with Off nothing is loaded into any game. The manifest path and `MUMCORD_OVERLAY_LAYER` override live in `src-tauri/src/ingame_overlay/manifest.rs`. For Steam games the launch-option alternative is the OpenGL preload: `LD_PRELOAD=…/libmumcord_overlay_layer.so %command%`; the per-game opt-out is `MUMCORD_OVERLAY_DISABLE=1 %command%`. To find out why nothing shows in a game, `MUMCORD_OVERLAY_DEBUG=1 PROTON_LOG=1 %command%` makes the Vulkan layer write `[mumcord-overlay]` lines to stderr (swapchain format and flags, what Mumcord sent as counts only, and every 5 s how many presents got the overlay and why the others did not); with Proton they land in `~/steam-<appid>.log`. Mumcord itself logs each config and scene it sends at `debug` level (counts only). The overlay image sits in two texture slots so a new image can be uploaded while earlier frames that show the old one are still on the GPU, which is always the case under DXVK/vkd3d-proton and in GPU-bound games.
- **Allow decision (QA.55/QA.56).** `mumcord_engine::decide_overlay(settings, key)` → `show | globalOff | gameOff | blocked`. Drawn only if the global mode is On **and** the game is not switched off **and** (not on the bundled blocklist, or blocklisted with an explicit confirmed override). The blocklist (`crates/engine/src/ingame_overlay/blocklist.json`, sourced: game, anti-cheat, reason, source URL — Valorant/LoL Vanguard, CoD Ricochet, CS2-on-FACEIT, PUBG BattlEye, Apex EAC) keeps those games off by default even when On; enabling one needs `riskConfirmed`.
- **Settings model** (`crates/store`, field `ingame_overlay`): `mode: Off|On` (default Off), and `games: [{ key (Steam app id or exe), name, enabled: null|bool, riskConfirmed, corner, sizePercent, opacityPercent, showWholeChannel, showChannelName }]`, persisted with serde defaults (no migration).
- **Commands / events** (area `ingame_overlay`): `ingame_overlay_state → InGameOverlayState { supported, explanationKey, mode, games[], known[] }` (each `games` entry carries its `blocklist` info and current `effective` effect; `known` lists games running now or on the blocklist, to add), `ingame_overlay_set_mode(mode)`, `ingame_overlay_set_game(entry)`, `ingame_overlay_remove_game(key)`. All three persist, re-apply the manifest and emit `inGameOverlayChanged { state }`. `GameKey` is `{ kind: "steam", value: number } | { kind: "exe", value: string }`.
- **Wizard.** The last step offers "Show the overlay inside games" (default off, hidden where unsupported) with an example screenshot (`ui/src/assets/ingame-overlay-example.png`) and the anti-cheat note; choosing it calls `ingame_overlay_set_mode("on")`.
- **Verification.** Linux end-to-end is proven headless: `cargo run -p mumcord-overlay-layer --example headless_check` (Vulkan) and `… --example egl_check` with the library in `LD_PRELOAD` (OpenGL) start a mock Mumcord, present frames through the layer and assert the talking indicator is drawn; the same manifest + env also works under `vkcube`. The Windows window is checked by unit tests of its pure logic (`follow.rs`: game detection, show/hide, corner placement) and manually on Windows (AC-2.20).

## History sync

History sync (FR-1.60, FR-1.60b, QA.48–QA.50) lets Mumcord clients fill each other's channel history; the server keeps none. Engine side: `crates/engine/src/history_sync/`; store side: `chat_message.synced_from` (schema v9).

- **Transport:** plugin data (`PluginDataTransmission`, servers ≥ 1.4) with data id `mumcord.history`. Each packet is a compact JSON header (`{"v":1,"t":…}`), optionally followed by `\n` and a binary body, at most 1000 bytes (server limit). Kinds: `areq` (who holds channel `c` in `[from, to)`, sent to everyone), `avail` (holder's summary: count `n`, oldest/newest time, no content), `hreq` (send me your hash list), `hashes` (chunked 8-byte content hashes, oldest first), `get` (bitmap over that list: the messages to send), `part` (chunked JSON array of `{ts, n, h, b}`), `deny`. Unknown versions and malformed packets are ignored.
- **Flow:** joining or following a channel (and every own channel after connect) queues a sync of that channel; channels are synced one at a time. The client asks everyone for summaries, waits 1.5 s, asks the up to 3 largest holders for their hash lists, drops every hash it already has, assigns each missing hash to exactly one holder (evenly spread) and fetches only those. At most 7 days back and 500 messages per request (the newest 500 before the cutoff); bodies over 8 KB (inline images) are not synced.
- **Cutoff (QA.49):** only messages older than the moment the requester started receiving the channel live: the join time for the own channel, the follow time for a followed channel, the connect time for both after a (re)connect. Holders clamp every request to the moment _they_ saw the requester enter or follow the channel and answer only people who currently receive it; channel messages only, never private chats.
- **Deleted history stays deleted (issue #119):** "Clear history" (one channel, a server or everything) stores the time of the clear in `history_cleared` (schema v12, local only). A sync of a channel then starts its range after the latest clear that covers it (plus 5 s for holders whose clocks run ahead), and with "Delete chat history older than N days" on, not before that window either. The start goes out as the existing `from` field of `areq` and `hreq`, which every Mumcord version honors, so there is no new field and older clients answer correctly. The requester also drops every received message before that start, including messages from a clear made during the sync, so a holder that ignores `from` cannot bring deleted messages back. Clearing only affects this device: other people keep their copies. When the start is not before the cutoff, nothing is requested and `historySyncStatus` ends right away with `added: 0`.
- **Content hash (QA.48):** first 8 bytes of SHA-1 over channel path, sender (certificate hash, or name for users without one), send time rounded down to the second and the body's normalized text (tags removed, common entities decoded, whitespace collapsed; markup only when there is no text). Mumble has no server timestamps, so every client stamps messages with its own receive time; matching accepts ±1 s. Clocks that differ by more than that can produce duplicates.
- **Untrusted input:** received messages must match a requested hash (recomputed from the content), lie inside the requested range and size limits; names are cleaned and bodies go through the same sanitizer as live chat (`sanitize_message_html`) before they are stored or emitted. Data that does not answer an own open request is ignored.
- **Limits:** outgoing packets are paced at 3 per second (burst 10, below murmur's default plugin message limit of 4/s, burst 15) and sent round robin per receiver. Holders accept about one request per 5 s per person (burst 6), keep at most 3 answers open (others get `deny`), send at most 256 KB per answer, and drop answers whose `get` does not follow within 60 s. Requesters give up on a holder after 15 s without hash chunks or 30 s without message chunks.
- **Sharing switch:** `Settings.history_sharing` (on by default). Off: the client answers nothing (summaries stay silent, hash requests get `deny`); it still requests history itself.
- **Command:** `Engine::history_sync_request(channel_id, before)` – "Load earlier messages": syncs the channel up to `before` (Unix ms, e.g. the oldest shown message) or its cutoff. Errors: `notFound` when the channel is neither joined nor followed, `serverTooOld` on servers without plugin data.
- **Storage:** synced messages are stored like live ones (respecting "Save history"), ordered by `sent_at`, with the holder's name in `synced_from`; `Store::synced_origins(ids)` returns it for loaded history. Messages that could not be stored get a `tmp-` id.

## Friends

- **Storage:** friends are kept locally by certificate hash (with the last known name, the date added and when they were last seen), so they stay the same person across servers and renames (FR-1.64). People without a certificate cannot be friends; `friend_add` answers `invalidInput` for them and for the own session.
- **Online state:** a friend is online while someone with their certificate is on the connected server; `online` names the server, session and channel. When they leave or the connection ends they go offline and `lastSeenAt` is updated. The list is sorted online first, then by name.
- **Private history (FR-1.65):** the private chat with a friend is read across all servers by certificate hash, and automatic history deletion leaves it alone. "Clear history" of that chat still deletes it (on all servers).

## Connection statistics

`connection_stats(serverId)` returns `ConnectionStats` of the own connection to that server:

- `transport`: `udp` / `tcp`, or `null` if the voice transport could not be started.
- `rttMs`: smoothed UDP ping round-trip time, or `null` until measured and while voice is tunnelled over TCP.
- `lossPercent`: recent packet loss in whole percent, 0–100 (the larger of the server → client loss and unanswered UDP pings; always 0 on TCP).
- `sendBitrateKbps`: the current Opus encoder target set by the adaptive bitrate controller (FR-1.24). It drops when the link is lossy (AC-1.23) and recovers when it is clean again.
- `serverMaxBandwidthKbps`: the server's per-user bandwidth limit, or `null` if it announced none.
- `packetsSent` / `packetsReceived`: voice packets sent and received since the current connection (or reconnect) started.
- `audio`: health of the local audio path since voice started on this connection, or `null` on a server without voice (issue #123). Rising counts tell where crackles or dropouts come from:
  - `dropouts`: problems the audio devices reported or ran into (host xruns, stream restarts, captured audio that did not fit, playback that ran dry).
  - `lateFrames`: frames the capture or playback thread handled too late because the CPU was busy elsewhere.
  - `concealedFrames`: received frames rebuilt by packet-loss concealment because packets came late or not at all (network).
  - `jitterBufferMs`: the current jitter-buffer delay of the people talking; it grows while packets arrive unevenly.
  - `processingAvgUs` / `processingMaxUs`: average and worst time to process one captured 10 ms frame (echo cancellation, noise suppression, automatic gain, Opus).
  - `realtime`: whether the voice threads got real-time scheduling (rtkit on Linux, MMCSS on Windows, a time-constraint policy on macOS). Without it they run at normal priority and are more easily delayed under load.

It is a command the UI polls about once per second while the connection info panel is open, not a periodic event: nothing is computed or sent while nobody looks, and the event stream stays free of noise. The same figures, plus the crypto good/late/lost counters and the audio counters in full detail (per direction, with mixing time), are written to the diagnostic file (`diagnostics_save`).

## Packet inspector

A hidden debugging view (issue #60, [packet-inspector.md](packet-inspector.md)). While the developer tools are unlocked the UI calls `packet_capture_set(true)`; the engine then keeps the last 2,000 control-channel packets of every connection in memory. Nothing is logged or sent anywhere, and `packet_capture_set(false)` drops it all.

`packet_capture_poll(after)` returns `PacketCapture`:

- `capturing`: whether capture is on.
- `packets`: `Packet`s with an id above `after` (all kept ones with `null`), oldest first. Each has `id`, `serverId`, `atMs` (Unix milliseconds), `direction` (`sent` / `received`), `kind` (plugin data id such as `mumcord.watch`, or the Mumble message name such as `UserState`), `pluginData`, `size` (bytes of the plugin data, or of the whole message), `sender` / `receivers` (sessions, plugin data only), `delayMs` / `tokensLeft` (client pacer, sent plugin data only), `decoded` (pretty-printed JSON of the payload or `null`) and `rawHex` (plugin data only). Plugin data and names come from other clients: render as plain text.
- `counters`: packets per server, kind and direction since capture started or was cleared, including those the ring buffer dropped.
- `voice`: audio packets sent and received per connected server since its voice link started. Voice is counted, never captured.

The UI polls every 250 ms while the inspector is open, which batches the updates; nothing is pushed as events.

The inspector has its own window (label `packet-inspector`). Its capability allows only listening to events and the save dialog, and the command handler refuses every command for it except `packet_capture_poll`, `packet_capture_clear`, `packet_capture_export`, `app_info`, `packet_inspector_view` and `packet_inspector_close`. It gets theme, language and names from the main window through `packet_inspector_share` / `inspectorViewChanged`. `packet_capture_set(false)` closes it.

The third-party licences (About → Show third-party licences) have their own window as well (label `licences`). It reads the static `third-party-notices.json` of the UI (scripts/generate-notices.sh). Its capability allows only listening to events, and the command handler refuses every command for it except `window_look`, `licences_close`, `copy_text` and `open_link`.

"What's new" (About → What's new) has its own window too (label `changelog`, issue #145). It reads `changelog.json`, which the Vite build generates from CHANGELOG.md (`vite.config.ts`), and calls `app_info` for the running version. The main window opens it once after an update: when the display version differs from `whatsNewSeen`, the wizard was finished before this start and `whatsNewAuto` is on; dev builds never open it. Its capability allows only listening to events, and the command handler refuses every command for it except `window_look`, `changelog_close`, `copy_text`, `open_link` and `app_info`.

The chat pins the welcome text in the root channel and in the default channel when that channel has no description (FR-1.48b).
- `ChannelInfo`: `{ id, parentId, name, position, permissions: { enter, textMessage, listen, registerSelf }, description, hasDescription }`. `registerSelf` is only meaningful on the root channel. `description` is sanitized HTML or `null`; `hasDescription` is true when the channel has a description even if the server only announced its hash, in which case `description` stays `null` until `channel_description_request` fetches it (FR-1.48b).
- `User`: `{ session, channelId, name, certHash, registered, selfMute, selfDeaf, serverMute, serverDeaf, suppressed (no Speak permission in the current channel), listeningChannelIds, hasAvatar, avatarHash (hex texture hash or null; changes when the avatar is replaced), hasComment, volume, localMute, isMumcord (the person sent a Mumcord hello, FR-1.61), mumcordFeatures (what that client announced; empty otherwise) }`. Recognition uses plugin data id `mumcord.hello` with `{"app":"mumcord","v":1,"features":[…]}`, sent on connect and to people who join, answered once per peer; official clients ignore it.
- `ChatMessage`: `{ id, conversation, senderName, senderCertHash, senderSession, own, sentAt, body, dismissedPreviews, syncedFrom }`. `body` is sanitized HTML; the UI sanitizes again before rendering. `dismissedPreviews` lists the links whose preview card the user hid (`preview_dismiss`); it is filled by `history_load` and empty for live messages. `syncedFrom` is the name of the person whose history the message was synced from (FR-1.60), also after `history_load`; `null` otherwise.

## UI client and mock

`ui/src/api/` contains:

- `client.ts`: the `MumcordApi` interface, derived from the generated bindings so it cannot drift from Rust. Commands resolve with data or reject with `EngineError`; `on(event, handler)` returns an unsubscribe function.
- `tauri.ts`: the real client, wrapping the generated bindings.
- `mock.ts`: `createMockApi(options)`, an in-memory engine with a seeded server (Root, Lobby, Raid, AFK; Anna, Ben, Carla). It also exposes `api.mock` test controls: `emit`, `failNext`, `requireCertTrust`, `receiveMessage`, `loseConnection`, `completeReconnect`, `setTalking`.
- `index.ts`: `getApi()`, `setApi()` and `selectApiKind()`.

How the implementation is chosen:

1. `VITE_MUMCORD_MOCK=1` uses the mock in any build.
2. Inside the Tauri webview, the real engine is used.
3. Outside Tauri, the mock is used only in dev or test builds (`vite dev`, vitest).
4. A production build outside Tauri throws instead of silently using the mock.

Tests can inject a client with `setApi(createMockApi({ seed: "fresh" }))` and reset it with `setApi(undefined)`.
