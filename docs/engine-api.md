# Engine API contract (Stage 1a)

This is the contract between the React UI and the Rust engine, exposed through Tauri commands and events. Covers Epic 1, Stage 1a (`specs/01-foundation-specification.md`, FR-1.1–FR-1.40). Stage 1b (positional audio, overlay) adds to it later.

- **Source of truth:** Rust types and handlers in `src-tauri/src/commands/<area>.rs`, registered in `specta_builder()` in `src-tauri/src/lib.rs`.
- **Generated TypeScript:** `ui/src/bindings/commands.ts`. It is regenerated by debug runs and by `cargo test -p mumcord`. Never edit it by hand.
- **UI access:** always go through `getApi()` from `ui/src/api`, never the bindings directly. See [UI client and mock](#ui-client-and-mock).
- **Naming:** Rust `snake_case` commands become camelCase in TS (`identity_get` → `api.identityGet()`). Payload fields are camelCase. Simple enums are camelCase string literals; enums with data are tagged objects (`kind`, `state` or `status` field).
- **Numbers:** ids are `u32` (TS `number`) and times are RFC 3339 strings, because 64-bit integers are not exported to TS.
- **Optional values:** `Option<T>` is a required field of type `T | null`.

## Errors

Every command returns `Result<T, ApiError>`, with `ApiError = { code: ErrorCode, message: string }`. In the UI client a failure rejects with `EngineError` (`code`, `message`). `message` is technical detail or the server's denial text. The UI shows a plain-language text based on `code`. Messages never contain secrets.

| Code                       | Meaning / typical source                                                                      |
| -------------------------- | --------------------------------------------------------------------------------------------- |
| `notImplemented`           | Contract exists, engine part not built yet (all stubs today).                                 |
| `notConnected`             | The command needs an active connection.                                                       |
| `serverUnreachable`        | DNS failure, connection refused or timeout.                                                   |
| `wrongPassword`            | Server password rejected.                                                                     |
| `nameInUse`                | Username already in use or registered to someone else.                                        |
| `certificateRejected`      | Server rejected the client certificate, or the user declined to trust the server certificate. |
| `certificateChanged`       | A trusted server presented a different certificate (FR-1.10).                                 |
| `serverTooOld`             | Feature needs a newer server, e.g. following needs ≥ 1.4 (FR-1.12).                           |
| `permissionDenied`         | The server's ACL denied the action; `message` has the server's reason.                        |
| `listenerLimitReached`     | The server's channel-listener limit is reached (FR-1.31).                                     |
| `messageTooLarge`          | Message, image or avatar exceeds the server limit (FR-1.30).                                  |
| `invalidInput`             | Bad argument: empty name, bad address, malformed link, out-of-range volume.                   |
| `notFound`                 | Unknown server, channel, person or file; also "no identity yet".                              |
| `secureStorageUnavailable` | OS secure storage unavailable or access refused (FR-1.3, FR-1.8).                             |
| `io`                       | Reading or writing a local file failed.                                                       |
| `shortcutNotConfirmed`     | Wayland: the desktop did not confirm the PTT shortcut (dismissed, no key, portal error).      |
| `internal`                 | Unexpected failure. In the UI also used for framework-level IPC errors.                       |

Some server denials arrive later, not as a reply to a command. Those come as the `serverDenied` event.

## Shared types

- `ServerId`, `ChannelId`, `SessionId` are `number`. Channel and session ids are only valid for the current connection.
- `Conversation`:
  - `{ kind: "channel", channelId }`
  - `{ kind: "private", certHash }`: private chat with a person, kept across sessions.
  - `{ kind: "privateSession", session }`: private chat with a person who has no certificate; lasts only for the session.

`Settings` fields:

- `wizardCompleted`: boolean.
- `theme`: `system` / `dark` / `light`.
- `language`: `en` / `es` / `de`, or `null` to follow the OS.
- `talkMode`: `voiceActivation` / `pushToTalk`.
- `voiceActivation`: `automatic` (default, speech detection) / `manual` (FR-1.57). Only matters in `voiceActivation` talk mode. In `manual` the mic opens when the processed input level (after echo cancellation, noise suppression and automatic volume, the same value the `micLevel` meter shows) reaches `voiceThresholdDbfs`; the gate opens on the first 10 ms frame, stays open 300 ms after the level drops and uses 3 dB of hysteresis.
- `voiceThresholdDbfs`: integer, -60 to 0, default -40; clamped on save. Map to the 0–1 `micLevel` scale with `(dbfs + 60) / 60`.
- `pttKey`: string or `null`; a keyboard shortcut (`"Ctrl+A"`) or a mouse button (`"MouseMiddle"`, `"Mouse4"` = back, `"Mouse5"` = forward).
- `allowMouseButtons`: boolean, default `false`. Linux Wayland only: "Allow mouse buttons (requires input group)".
- `pttCompatibilityMode`: boolean, default `false`. Linux Wayland only: "Compatibility mode (like TeamSpeak)". Read before GTK starts: when on, Mumcord sets `GDK_BACKEND=x11` (unless the user set it), runs through XWayland and uses the X11 push-to-talk path for keys and mouse buttons (no portal, no evdev). Takes effect after `app_restart` (FR-1.48).
- `inputDevice`, `outputDevice`: device id, or `null` for the OS default.
- `noiseSuppression`, `echoCancellation`, `autoGain`: boolean.
- `musicQuality`: boolean, default `false` (FR-1.24, QA.37). Off: the automatic send bitrate is capped at 96 kbit/s (speech). On: the cap is the server limit minus 10 % headroom and packet overhead, at most 510 kbit/s; the Opus encoder switches to the audio application with the music signal type; noise suppression and automatic volume are bypassed (they damage music). The bitrate still drops on packet loss and recovers afterwards; `sendBitrateKbps` in `connection_stats` shows the current value. Applies immediately, also while connected. Voice activation may not open for music, so push-to-talk is advised.
- `sounds`: `{ joinLeave, selfMute, selfDeaf, messages, voiceJoin, hangUp }`. `voiceJoin` plays when the user joins a channel for voice themselves (join command or a link with a channel; not the read-only landing or a reconnect). `hangUp` plays on `disconnect` and when `connect` replaces a connection with voice on, not on quit or connection loss.
- `notifications`: `"inApp" | "desktop" | "both" | "off"` (default `"both"`, FR-1.48c). In-app: toasts while the window has focus, nothing otherwise. Desktop: system notifications, also while focused. Both: toasts while focused, system notifications otherwise. Never for the chat on screen while focused.
- `closeBehaviour`: `ask` / `minimizeToTray` / `quit`.
- `chatDisplay`: `"cozy" | "compact"` (default `"cozy"`, FR-1.48a, QA.25). Cozy: avatar per message group, name and time above the indented text. Compact: no avatars, time, name and text on one line.
- `logLevel`: `error` / `warn` / `info` / `debug`.
- `sendDefaultAvatar`: boolean, default `true`. On the first connect to a saved server, the default avatar is sent if one is set and the user has no avatar there yet, scaled to the server limit. Each saved server is handled only once, whatever the outcome (setting off, no default avatar, already an avatar there, sent, or too large): it is never sent there again, even after the user removes or replaces the avatar manually. Only failures such as a lost connection or a denial leave the server unhandled for the next connect (FR-1.47). A sent default avatar becomes the avatar remembered for that server (see `set_own_avatar`), so it is sent again whenever the server has forgotten it (QA.10).
- `autostart`: boolean, default `false` (FR-1.48d). Changing it adds or removes the OS login entry (Linux `$XDG_CONFIG_HOME/autostart/app.mumcord.client.desktop`, macOS `~/Library/LaunchAgents/app.mumcord.client.plist`, Windows `HKCU\…\Run\Mumcord`) before saving; if that fails, `settings_update` fails with `internal` and nothing is saved. Every start rewrites the entry for the current program path (e.g. a moved AppImage) or removes a leftover one. The entry starts Mumcord with `--autostart`.
- `startMinimized`: boolean, default `true`. A start through the login entry keeps the window hidden in the tray (minimized to the taskbar if no tray is available); a manual start always shows the window.
- `connectMuted`: boolean, default `true` (FR-1.14, QA.22). On: a fresh connect without a link lands read-only (self-muted and deafened) until the user joins a channel. Off: it lands in the default channel with the user's last own mute/deafen choice applied right away, without the read-only hint and without the join sound; the rejoin prompt (QA.9) is still offered. A link with a channel path and an automatic reconnect behave as before. Read at each connect, no restart needed.
- `linkPreviews`: boolean, default `true` (FR-1.49, QA.34). "Show link previews and embeds", offered in the first-start wizard (step 3) and under Settings → Chat & history. Off: messages show plain links and `link_preview` makes no request.
- `previewCacheDays`: number or `null`, default `7` (QA.42). "Delete cached previews after X days" under Settings → Chat & history (1 / 7 / 30 / never). Values below 1 are stored as 1. Applied at start, hourly and right after a change.
- `historyMaxAgeDays`: number or `null`, default `null` (keep everything; QA.42). "Delete chat history older than X days" under Settings → Chat & history (7 / 30 / 90 / 365). Deletes messages sent before now minus X days on every server, without confirmation, at start, daily and right after a change; local history only.
- `nowPlaying`: boolean, default `false` (FR-1.58, QA.40). "Share what I'm listening to" under Settings → Profile. Off: the media player is not read, nothing is shared and the comment line is removed.
- `nowGaming`: boolean, default `false` (FR-1.59, QA.44). "Share the game I'm playing" under Settings → Profile and in the quick settings. Off: no programs or Steam files are read, nothing is shared and the comment line is removed.

Mouse push-to-talk (FR-1.21, QA.4): `native` support means a Windows low-level mouse hook, a macOS listen-only event tap (`accessibilityMissing` if the system refuses it; the system prompt is shown) or X11 XInput2 raw button events. `evdev` (Linux Wayland) reads input devices directly and only while `allowMouseButtons` is on: it opens only mice (`BTN_LEFT` and relative motion, no letter or digit keys), never grabs them, evaluates only the configured button and logs no input; mice plugged in later are picked up. Its `state` is the device permission, checked without opening a device, also while the setting is off. `inputGroupMissing`: the UI shows `sudo usermod -aG input $USER`, then log out and in. `mouseDisabled`: a mouse key is stored but `allowMouseButtons` is off.

## Link previews and player cards

`link_preview` (FR-1.49, FR-1.50) returns `LinkPreview { url, siteName, title, description, image, video, isImage }`. All text is plain text (whitespace collapsed, control and bidi characters removed, length-limited); the UI renders it as text, never as HTML. `image` is a `data:image/jpeg|png` URL: the engine fetches the preview image itself, decodes it with size limits, scales it to at most 480 px and re-encodes it, so the webview never loads anything from the linked site. `video` is set for YouTube (`youtube.com/watch`, `youtu.be`, `/shorts`, `/live`) Twitch (channel, `/videos/<id>`, clips) and Spotify (`open.spotify.com/{track,album,playlist,artist,episode,show}/<id>`, optional `intl-xx/` prefix, query like `?si=` ignored) links: `VideoEmbed { site: "youtube" | "twitch" | "spotify", playerUrl, channel }`. For Spotify `channel` is the kind of item (`track`, `album`, …) and `description` is the artist/owner line from the page's OpenGraph tags.

- **Fetching** (`crates/engine/src/web/`): GET with a neutral User-Agent, no cookies, no referrer, no proxy, 4 s connect / 8 s total timeout, at most 3 redirects, HTML read up to 512 KB (only `<head>` metadata is used: OpenGraph, Twitter cards, `<title>`, `<meta name="description">`), images up to 2 MB (PNG, JPEG, GIF, WebP, detected from the bytes). YouTube titles, uploader and thumbnail come from YouTube's public oEmbed endpoint; Twitch from the page's OpenGraph tags; Spotify title and cover from Spotify's public oEmbed endpoint (`open.spotify.com/oembed`, no key), falling back to the page's OpenGraph tags.
- **SSRF guard:** private, loopback, link-local, carrier-grade NAT, multicast, documentation and other non-public addresses (IPv4 and IPv6, including IPv4-mapped and 6to4) are never contacted. Host names are resolved by a resolver that drops such addresses at connect time, so DNS rebinding and every redirect hop are covered; IP literals are checked before the request and on each redirect. E2E builds (`test-backend`) can restrict fetching to given addresses with `MUMCORD_TEST_PREVIEW_ADDRESSES`.
- **Cache:** every result (also "no preview") in memory, successful previews also on disk in `<data dir>/link-previews/` (one JSON file per URL hash, at most 300 files) for `previewCacheDays` days (default 7, QA.42). Thumbnails and preview images are part of the cached preview, so one clean-up covers all of them. Expired files are deleted at start, hourly and after the setting changes, off the UI thread; `preview_cache_clear` deletes everything. Failures are retried after 10 minutes (memory only).
- **Player:** the UI loads `playerUrl` in an iframe only after the user clicks play (`sandbox="allow-scripts allow-same-origin allow-presentation"`). Twitch needs `parent=<page host>` appended. The CSP in `src-tauri/tauri.conf.json` allows `frame-src` for exactly `https://www.youtube-nocookie.com`, `https://player.twitch.tv`, `https://clips.twitch.tv` and `https://open.spotify.com/embed/` (Spotify only on the embed path); images stay limited to `'self' data: blob:`.
- **Platform limits:** YouTube refuses to play without an http(s) referrer, which pages served from Tauri's `tauri://` scheme (Linux with WebKitGTK, macOS) cannot send; Twitch only accepts an HTTPS or `localhost` parent, which Windows' `http://tauri.localhost` is not. Spotify's embed needs neither, so its player is loaded on every platform; this could not be checked on WebKitGTK, WebView2 and WKWebView without internet access in the build environment, so verify it on a real Spotify link (if the widget stays blank in the app origin, make `playerUrl` return `null` for Spotify to fall back to the browser). Where a player cannot run, the play button opens the link in the system browser instead (tooltip "Plays in your browser"). Today that means YouTube plays inline on Windows and in the dev build, Twitch only in the dev build.
- **Image links:** a link whose response has an `image/*` content type yields `LinkPreview { isImage: true }` (no card); the UI shows it with `inline_image` instead.

## Inline images

`inline_image` (FR-1.55, QA.35) returns `InlineImage { url, src, width, height, animated }` for external images in messages and direct image links. Chat messages keep absolute http(s) `<img src>` URLs through the engine sanitizer (`sanitize_message_html`; comments and welcome texts never do); the UI sanitizer still removes these images from the message text and shows them under it instead. The UI treats links whose path ends in `.png`, `.jpg`, `.jpeg`, `.gif` or `.webp` as images directly, and other links as images when `link_preview` reports `isImage`.

- **Fetching:** the same guarded fetcher as link previews (SSRF guard incl. redirects, timeouts), up to 16 MB. Known GIF hosts first try smaller renditions (Giphy: `giphy.webp`, `200w.webp`, `200w.gif` next to a `media*.giphy.com` GIF; page links `giphy.com/gifs/<slug>-<id>` resolve by id, `tenor.com/view/<slug>-<id>` by the page's `og:image`); `link_preview` reports `isImage` for these page links. The result keeps the link as posted. The format is sniffed from the bytes (PNG, JPEG, GIF, WebP); the server's content type is ignored. Images larger than 8192 px per side are refused.
- **Delivery:** `src` is always a `data:` URL, so the CSP stays unchanged. Still images are decoded with limits, scaled to at most 800 px per side (twice the 400×300 chat box) and re-encoded as JPEG or PNG. Animated GIF and WebP pass through unchanged so they keep moving, if no side exceeds 2048 px. `width`/`height` describe `src`, so the UI reserves the right box (a fixed 400×300 placeholder while loading).
- **Cache and privacy:** cached like previews in `<data dir>/link-previews/images/` (at most 150 files) and removed by the same `previewCacheDays` clean-up and "Clear now". Dismissing uses `preview_dismiss` with the image URL. Off switch (`linkPreviews`): nothing is fetched, the images are not shown (AC-1.13 behaviour).
- **Click:** the UI's `onImageClick` hook (image viewer, B42); until then a click opens the image in the browser.

## Now playing

"Now playing" (FR-1.58) shares the track playing in the system's media player with others on the server; it is opt-in (`nowPlaying` setting).

- **Source** (`src-tauri/src/now_playing/`): read every 2 s off the UI thread, only while the setting is on. Linux: MPRIS over the session D-Bus (`org.mpris.MediaPlayer2.*`; a playing player wins over a paused one, Spotify over others; title, artists, album, `mpris:artUrl`, length, position). Windows: the system media session (`GlobalSystemMediaTransportControlsSessionManager`; no cover, Windows exposes it only as an image stream). macOS: not supported (no public API); `now_playing_status` reports `supported: false`.
- **Sharing** (`crates/engine/src/now_playing/`): plugin data (`PluginDataTransmission`, servers ≥ 1.4) with data id `mumcord.nowplaying` and the JSON payload `{"v":1,"title","artist","album","art","pos_ms","dur_ms","playing","ts"}` (`{"v":1}` = stopped), at most 1000 bytes (the server limit; the cover link goes first, then the album, then title and artist are shortened). Sent to everyone on the server on every change (track, play/pause, a seek of more than 3 s) and every 30 s, and to people who join. Received payloads are capped and sanitized; only http(s) cover links are kept.
- **Comment line:** official clients see `🎵 Artist – Title` at the end of the own comment while a track plays. It changes only after a change has lasted 5 s (no update per skipped track), is removed when playback pauses or stops, the setting is turned off or the user disconnects (best effort; a leftover line is removed on the next connect), and is left out if the comment would exceed the server's text limit. `set_own_comment` keeps the line; `person_profile` of the own session returns the comment without it.
- **Display:** `nowPlayingChanged` events; the UI anchors `positionMs` to the arrival time and advances it locally while playing. Music icon with tooltip next to the person while playing; cover, title, artist and progress bar in the profile card and preview.

## Now gaming

"Now gaming" (FR-1.59) shares the game being played with others on the server; it is opt-in (`nowGaming` setting). It mirrors [Now playing](#now-playing).

- **Sources** (`src-tauri/src/now_gaming/`, parsing in `crates/engine/src/now_gaming/detect.rs`): asked every 5 s off the UI thread, only while the setting is on, best first through the engine's `GameSource` trait (the Mumble Link source with game name and context arrives with positional audio, B30, in front of the others).
  1. The running Steam game. Linux: the app id of Steam's `reaper SteamLaunch AppId=<id> -- …` wrapper, which Steam starts every game under (its command line is world-readable, unlike the `SteamAppId` environment variable, and current Steam clients no longer write `RunningAppID` to `~/.steam/registry.vdf` – that file is only a fallback). Windows: `HKCU\Software\Valve\Steam\RunningAppID` (via `reg query`). macOS (best effort): `RunningAppID` in `~/Library/Application Support/Steam/registry.vdf`. The name comes from the bundled list, else from the game's `appmanifest_<id>.acf` in Steam's libraries (Linux/macOS; native, Flatpak and `~/.steam` installs) or `HKCU\Software\Valve\Steam\Apps\<id>\Name` (Windows).
  2. Running programs (Linux `/proc`, Windows `tasklist`, macOS `ps`) matched by executable name against the bundled list `crates/engine/src/now_gaming/games.json` (about 75 well-known games: name, optional Steam app id, executable names per OS; on Linux the Windows names count too, for Proton).
     Support: Linux and Windows full; macOS best effort (few macOS entries, Steam rarely records the running game there); other systems report `supported: false`.
- **Sharing** (`crates/engine/src/now_gaming/`): plugin data id `mumcord.nowgaming`, JSON `{"v":1,"game","steam_app_id","started_at","join"}` (`{"v":1}` = stopped; `started_at` in Unix ms of the sender; `steam_app_id` and `join` optional). Sent on every change and every 60 s, and to people who join. Received payloads are capped and sanitized; a start time in the future counts as now, and `join` is kept only when it is exactly `steam://connect/<host>:<port>` (plain host name or IPv4, port 1–65535).
- **Join target:** offered only when the own game was started with `+connect <host[:port]>` (Source engine games joined from a server browser; port 27015 when none is given). Lobby links and the Mumble Link context come later (B30). "Join game" asks for confirmation and then opens the link through the OS; other targets never get a button.
- **Comment line:** official clients see `🎮 Game` at the end of the own comment while a game runs; same rules as the now-playing line (5 s settle, removed when the game ends, the setting is turned off or the user disconnects). Both status lines can be present (music first); each feature only replaces its own.
- **Display:** `nowGamingChanged` events; the UI anchors `playedMs` to the arrival time. Controller icon with tooltip "Playing <game>" next to the person; game picture (or a generic controller), name and play time ("for 1 h 20 min") in the profile card and preview; "Join game" only in the profile card of another person. The own user panel status line shows the game in front of a playing track (one short line); its tooltip names both.

## Overlay

The overlay (FR-1.44–FR-1.46) is a second window, label `overlay`, page `ui/overlay.html` (entry `ui/src/overlay/`). It is transparent, undecorated, always on top, click-through, not focusable, hidden from the taskbar and on all workspaces. It exists only while the overlay is enabled, so a disabled overlay costs nothing. It reads the same engine events as the main window through the shared server store and draws nothing while nobody talks.

- **Content:** who is talking (avatar, name, green talking ring), in the order they started; after someone stops they stay for 1.5 s and fade out. `showWholeChannel` lists everyone in the own channel instead, talkers with the ring. `showChannelName` puts the own channel's name on top. `opacity` applies to the whole panel.
- **`OverlaySettings`:** `{ enabled, showWholeChannel, showChannelName, opacity (percent, 20–100, default 90), corner ("topLeft" | "topRight" | "bottomLeft" | "bottomRight", default topLeft), customPosition ({ x, y } physical desktop pixels, or null), width (logical px, 160–800, default 240), height (logical px, 80–1200, default 320) }`. Stored in the settings record (`overlay`), restored at start (the window reopens if it was enabled). While `customPosition` is set and still on a screen it wins over `corner`; the settings UI sends `customPosition: null` when the user picks a corner. Corners are in the primary screen's work area with a 16 px margin.
- **Move mode:** `overlay_move_mode(true)` turns click-through off and makes the window focusable; the page shows a dashed frame, "Drag to move the overlay" and a Done button (Escape also leaves). Dragging uses Tauri's drag region. `overlay_move_mode(false)` stores the window position as `customPosition` (not on native Wayland, where the position cannot be read).
- **`OverlayState`:** `{ settings, moveMode, onTopSupported, positionSupported, explanationKey, kdeWayland, kwinRuleInstalled, language }`. `explanationKey` is an i18n key in the `overlay` namespace (`limits.wayland`, `limits.waylandKde`) or `null`; settings show it when set (AC-1.34). `overlay:limits.exclusiveFullscreen` is the note for exclusive-fullscreen games and applies on every platform, so settings always show it. `language` is the settings language for the overlay page (`null` follows the OS).
- **Platforms:** Windows and macOS keep the overlay above windowed and borderless-fullscreen apps. Linux X11 honours "keep above" and positions. On a native Linux Wayland session an app can neither keep a window on top nor place it, so `onTopSupported` and `positionSupported` are `false`; KDE Plasma can force both with a window rule for the window titled "Mumcord overlay", and in push-to-talk compatibility mode (XWayland) the X11 behaviour applies. Click-through works everywhere (input region).
- **KDE window rule:** `kdeWayland` is true on native Wayland under KDE; then the overlay settings offer "Set up automatically", "Remove rule" (while `kwinRuleInstalled`), "Open KDE window rules" and "Use compatibility mode instead" (opens Settings → Voice and focuses that switch). The rule matches window class `app.mumcord.client` with title "Mumcord overlay" (normal windows) and forces keep above, position (the chosen corner of the primary screen, logical pixels), size, skip taskbar/pager/switcher and no focus. It is found again by its description, so installing twice updates it; other rules and keys in `kwinrulesrc` are kept. While the rule exists, changing the corner or size updates it and reloads KWin. A dragged place is not used (Wayland cannot report it).
- **Out of scope:** games in exclusive fullscreen draw over every window; the overlay never hooks into games (FR-1.44), so it is not visible there.
- **Security:** the overlay window has its own capability (`src-tauri/capabilities/overlay.json`: listen/unlisten to events, start dragging) and may call only `connection_state`, `session_snapshot`, `person_profile`, `overlay_state` and `overlay_move_mode`; every other command is refused for it (`overlay::may_invoke`). Same CSP as the main window.

## In-game overlay

The in-game overlay (FR-1.46b, AC-1.34b, QA.54–QA.56) is drawn **inside the game's own frames** (not a window), so it shows in exclusive fullscreen too. It is a separate pipeline from the window overlay above, which stays the fallback where this is off or unsupported.

- **Platforms.** Linux: a Vulkan layer (`VK_LAYER_MUMCORD_overlay`, crate `mumcord-overlay-layer`, built as `libmumcord_overlay_layer.so`) that hooks `vkQueuePresentKHR`, plus an OpenGL fallback in the same library loaded with `LD_PRELOAD` (`glXSwapBuffers`/`eglSwapBuffers`). Windows: a DXGI/Direct3D 11–12 hook DLL loaded into detected, allowed games — **designed but not built on the Linux CI host; not yet verified** (`SUPPORTED` is `false` there). macOS: none at all (QA.58; `SUPPORTED` is `false`, no window overlay either). `support()` in `src-tauri/src/ingame_overlay` returns `{ supported, explanationKey }`; on Linux it is supported only when the library is found (`MUMCORD_OVERLAY_LAYER`, else next to the executable, else `../lib/mumcord/`), otherwise `explanationKey` is `overlay.inGame.limits.libraryMissing`. `npm run build:overlay-layer` (run by `src-tauri/tauri.linux.conf.json` before `tauri dev`/`tauri build`) builds the library next to the app executable and stages it for the AppImage/deb/rpm, which install it as `/usr/lib/mumcord/libmumcord_overlay_layer.so`.
- **IPC.** Crate `mumcord-overlay-ipc` holds the protocol. Mumcord listens on a per-user abstract Unix socket `@mumcord-overlay-<uid>` (Linux; `MUMCORD_OVERLAY_SOCKET` overrides the name for isolated tests). It is abstract rather than a file in `$XDG_RUNTIME_DIR` because games in the Steam Linux Runtime (pressure-vessel, used by Proton) and Flatpak get a private runtime directory but share the host network namespace, where abstract sockets live. Abstract sockets have no file permissions, so both sides check the peer with `SO_PEERCRED`: Mumcord drops connections from other users, and the game refuses a listener owned by another user. Windows will use a per-user named pipe. A tiny versioned binary protocol (`wire.rs`, `VERSION`): the game sends `Hello { version, api, pid, steamAppId?, exe }`, Mumcord replies with `Config` (the per-game decision and look) and streams `Scene` (who is talking: names + talking/muted/deafened flags, the channel name) plus a `Heartbeat` every second. The game side reads non-blocking off the render thread and drops stale data (no heartbeat for 3 s → draw nothing); Mumcord never blocks on a stuck game (short write timeout, one thread per game).
- **Rendering.** The overlay is rasterized on the CPU into a premultiplied-RGBA panel (`render.rs`, bundled subset of Noto Sans Medium under SIL OFL 1.1, `crates/overlay-ipc/assets/`), then uploaded once per change and blended over the swapchain image (ONE / ONE_MINUS_SRC_ALPHA). Fail-open: any error, missing font or allocation failure draws nothing and never panics across FFI.
- **Install / uninstall.** Turning the global overlay **On** installs the Vulkan layer manifest into `"$XDG_DATA_HOME"/vulkan/implicit_layer.d/mumcord_overlay.json` (points at the `.so`, `disable_environment: MUMCORD_OVERLAY_DISABLE=1`); **Off** removes it, so with Off nothing is loaded into any game. The manifest path and `MUMCORD_OVERLAY_LAYER` override live in `src-tauri/src/ingame_overlay/manifest.rs`. For Steam games the launch-option alternative is the OpenGL preload: `LD_PRELOAD=…/libmumcord_overlay_layer.so %command%`; the per-game opt-out is `MUMCORD_OVERLAY_DISABLE=1 %command%`. To find out why nothing shows in a game, `MUMCORD_OVERLAY_DEBUG=1 PROTON_LOG=1 %command%` makes the Vulkan layer write `[mumcord-overlay]` lines to stderr (swapchain format and flags, what Mumcord sent as counts only, and every 5 s how many presents got the overlay and why the others did not); with Proton they land in `~/steam-<appid>.log`. Mumcord itself logs each config and scene it sends at `debug` level (counts only). The overlay image sits in two texture slots so a new image can be uploaded while earlier frames that show the old one are still on the GPU, which is always the case under DXVK/vkd3d-proton and in GPU-bound games.
- **Allow decision (QA.55/QA.56).** `mumcord_engine::decide_overlay(settings, key)` → `show | globalOff | gameOff | blocked`. Drawn only if the global mode is On **and** the game is not switched off **and** (not on the bundled blocklist, or blocklisted with an explicit confirmed override). The blocklist (`crates/engine/src/ingame_overlay/blocklist.json`, sourced: game, anti-cheat, reason, source URL — Valorant/LoL Vanguard, CoD Ricochet, CS2-on-FACEIT, PUBG BattlEye, Apex EAC) keeps those games off by default even when On; enabling one needs `riskConfirmed`.
- **Settings model** (`crates/store`, field `ingame_overlay`): `mode: Off|On` (default Off), and `games: [{ key (Steam app id or exe), name, enabled: null|bool, riskConfirmed, corner, sizePercent, opacityPercent, showWholeChannel, showChannelName }]`, persisted with serde defaults (no migration).
- **Commands / events** (area `ingame_overlay`): `ingame_overlay_state → InGameOverlayState { supported, explanationKey, mode, games[], known[] }` (each `games` entry carries its `blocklist` info and current `effective` effect; `known` lists games running now or on the blocklist, to add), `ingame_overlay_set_mode(mode)`, `ingame_overlay_set_game(entry)`, `ingame_overlay_remove_game(key)`. All three persist, re-apply the manifest and emit `inGameOverlayChanged { state }`. `GameKey` is `{ kind: "steam", value: number } | { kind: "exe", value: string }`.
- **Wizard.** The last step offers "Show the overlay inside games" (default off, hidden where unsupported) with an example screenshot (`ui/src/assets/ingame-overlay-example.png`) and the anti-cheat note; choosing it calls `ingame_overlay_set_mode("on")`.
- **Verification.** Linux end-to-end is proven headless: `cargo run -p mumcord-overlay-layer --example headless_check` (Vulkan) and `… --example egl_check` with the library in `LD_PRELOAD` (OpenGL) start a mock Mumcord, present frames through the layer and assert the talking indicator is drawn; the same manifest + env also works under `vkcube`. The Windows hook and injection remain to be built and verified on Windows.

## Connection statistics

`connection_stats` returns `ConnectionStats`:

- `transport`: `udp` / `tcp`, or `null` if the voice transport could not be started.
- `rttMs`: smoothed UDP ping round-trip time, or `null` until measured and while voice is tunnelled over TCP.
- `lossPercent`: recent packet loss in whole percent, 0–100 (the larger of the server → client loss and unanswered UDP pings; always 0 on TCP).
- `sendBitrateKbps`: the current Opus encoder target set by the adaptive bitrate controller (FR-1.24). It drops when the link is lossy (AC-1.23) and recovers when it is clean again.
- `serverMaxBandwidthKbps`: the server's per-user bandwidth limit, or `null` if it announced none.
- `packetsSent` / `packetsReceived`: voice packets sent and received since the current connection (or reconnect) started.

It is a command the UI polls about once per second while the connection info panel is open, not a periodic event: nothing is computed or sent while nobody looks, and the event stream stays free of noise. The same figures, plus the crypto good/late/lost counters, are written to the diagnostic file (`diagnostics_save`).

Payload types:

- `ServerInfo`: `{ version, followSupported, welcomeText, defaultChannelId, maxMessageLength, maxImageMessageLength, allowHtml }`. Length limits are in characters; 0 means unlimited. `welcomeText` is sanitized HTML; `defaultChannelId` is the channel the server put the user in on connect (its default channel, or the remembered one for registered users). The chat pins the welcome text in the root channel and in the default channel when that channel has no description (FR-1.48b).
- `ChannelInfo`: `{ id, parentId, name, position, permissions: { enter, textMessage, listen, registerSelf }, description, hasDescription }`. `registerSelf` is only meaningful on the root channel. `description` is sanitized HTML or `null`; `hasDescription` is true when the channel has a description even if the server only announced its hash, in which case `description` stays `null` until `channel_description_request` fetches it (FR-1.48b).
- `User`: `{ session, channelId, name, certHash, registered, selfMute, selfDeaf, serverMute, serverDeaf, suppressed (no Speak permission in the current channel), listeningChannelIds, hasAvatar, avatarHash (hex texture hash or null; changes when the avatar is replaced), hasComment, volume, localMute, isMumcord (the person sent a Mumcord hello, FR-1.61), mumcordFeatures (what that client announced; empty otherwise) }`. Recognition uses plugin data id `mumcord.hello` with `{"app":"mumcord","v":1,"features":[…]}`, sent on connect and to people who join, answered once per peer; official clients ignore it.
- `ChatMessage`: `{ id, conversation, senderName, senderCertHash, senderSession, own, sentAt, body, dismissedPreviews }`. `body` is sanitized HTML; the UI sanitizes again before rendering. `dismissedPreviews` lists the links whose preview card the user hid (`preview_dismiss`); it is filled by `history_load` and empty for live messages.

## UI client and mock

`ui/src/api/` contains:

- `client.ts`: the `MumcordApi` interface, derived from the generated bindings so it cannot drift from Rust. Commands resolve with data or reject with `EngineError`; `on(event, handler)` returns an unsubscribe function.
- `tauri.ts`: the real client, wrapping the generated bindings.
- `mock.ts`: `createMockApi(options)`, an in-memory engine with a seeded server (Root, Lobby, Raid, AFK; Anna, Ben, Carla). It also exposes `api.mock` test controls: `emit`, `failNext`, `requireCertTrust`, `receiveMessage`, `loseConnection`, `completeReconnect`, `setTalking`.
- `index.ts`: `getApi()`, `setApi()` and `selectApiKind()`.

How the implementation is chosen:

1. `VITE_MUMCORD_MOCK=1` uses the mock in any build.
2. Inside the Tauri webview, the real engine is used.
3. Outside Tauri, the mock is used only in dev or test builds (`vite dev`, vitest).
4. A production build outside Tauri throws instead of silently using the mock.

Tests can inject a client with `setApi(createMockApi({ seed: "fresh" }))` and reset it with `setApi(undefined)`.
